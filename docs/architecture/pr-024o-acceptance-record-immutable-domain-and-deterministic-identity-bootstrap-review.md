## 10. Canonical acceptance serialization

Canonical bytes are deterministic UTF-8 JSON with:

1. fixed key order matching `AcceptanceIdentityInput`;
2. Unicode NFC normalization for every string;
3. `ensure_ascii=False`;
4. compact separators with no insignificant whitespace;
5. no null values;
6. no omitted fields;
7. no path normalization;
8. no current clock;
9. no environment-dependent values;
10. exact UTC timestamp rendering.

### 10.1 Timestamp rendering

`accepted_at` is converted to UTC and serialized as:

`	ext
YYYY-MM-DDTHH:MM:SS.ffffffZ
`

Six fractional digits are always present.

Equivalent timezone offsets therefore produce identical canonical bytes.

Naive datetimes fail closed.

## 11. Digest and ID

The canonical bytes are hashed with SHA-256.

The lowercase 64-character digest is returned as `digest_hex`.

The acceptance record ID is:

`	ext
ar1_<digest_hex>
`

For PR-023E:

`	ext
canonical_acceptance_bytes_digest == AcceptanceIdentityResult.digest_hex
`

The repository must not recalculate this value using a different policy.

## 15. Relationship to EvidenceMaterializationContext

Before materialization, the caller must calculate the acceptance identity from explicit governance values.

The resulting `acceptance_record_id` is then supplied to `EvidenceMaterializationContext`.

The materializer continues to consume an explicit ID and does not generate governance identity.

No PR-024P modification to the materializer is authorized.

## 16. Replay and collision semantics

The identity contract supports later repository classification:

### Exact replay

Same `acceptance_record_id`, same canonical digest, and exact record equality.

### Governance replay candidate

Same `acceptance_record_id` and canonical digest, with differences limited to non-identity diagnostics.

No mutation or automatic merge is authorized by this contract.

### Same fact, new acceptance

Same `evidence_id` with a different valid `acceptance_record_id`.

Both governance events remain distinct.

### Acceptance collision

Same `acceptance_record_id` but a different canonical acceptance digest.

This fails closed.

## 17. Canonical digest boundary

`digest_hex` is both:

- the deterministic identity digest used by `ar1_`;
- the `canonical_acceptance_bytes_digest` required by future `EvidenceWriteRequest`.

No second acceptance digest algorithm or alternate serialization is permitted.

**Selected.** This closes the exact prerequisites identified by PR-024N.
